# Бриф схемы

Бриф — постановка задачи концептуализации, журнал решений и исполнимые сценарии в одном JSON. Метод, который за ним стоит, — [METHOD.md](METHOD.md). JSON-схема — [brief.schema.json](brief.schema.json).

Пока бриф хранится файлом `brief.json` в папке задачи, рядом с сессией (не в пакете rstool). Проверка схемы по брифу — скрипт `skills/scripts/check-brief.ts` (см. «Проверка»). В rstool 4.0 бриф переедет в сессию, а на Portal — в блок «Задание» паспорта схемы.

## Поля

| Поле             | Этап   | Что записать                                                                                                                                                        |
| :--------------- | :----- | :------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `status`         | 1      | `draft` — составляется; `confirmed` — пользователь подтвердил; `assumed` — спросить нельзя, ответы в `assumptions`                                                  |
| `approach`       | 1      | `research` — экспликация; `education` — обучение; `project` — основа для ПО / ОСС                                                                                   |
| `object`, `task` | 1      | объект исследования; задача и точка зрения — по одной-две фразы                                                                                                     |
| `source`         | 1      | документ и разделы, ссылка на схему Portal                                                                                                                          |
| `restrictions`   | 1      | что исключено (`excludes`) и что из-за этого невыразимо (`inexpressible`)                                                                                           |
| `expressiveness` | 1–3    | требования к выразительным средствам: `concept`, `ref` в источнике; `via` (этап 2) — как выразится через ядро; `constituent` (этап 3) — имя конституенты или `null` |
| `distinctions`   | 1, 4   | пары `between` (id требований `E#` или имена конституент) и `witness` — сценарий, где они различаются                                                               |
| `invariants`     | 1, 3–4 | правило `text`, аксиома `constituent`, сценарии `positive` и `negative`                                                                                             |
| `decisions`      | 2–3    | журнал: `topic`, `alternatives`, `choice`, `rationale`; `supersedes` — какое решение отменено                                                                       |
| `scenarios`      | 1–4    | маленькие интерпретации с ожиданиями (ниже)                                                                                                                         |
| `questions`      | 1–2    | вопросы раундов 1–2: `text`, `proposed`, `consequence`, `answer`                                                                                                    |
| `assumptions`    | 1–2    | то, что не спросили или не смогли спросить                                                                                                                          |
| `openQuestions`  | любой  | что осталось нерешённым, в том числе то, что ЯРЭ не выражает                                                                                                        |

Идентификаторы: `L#` ограничения, `E#` требования, `V#` различения, `I#` инварианты, `DC#` решения, `SC#` сценарии. Идентификатор не переиспользуется после удаления.

Ссылки на конституенты — по имени (`D3`). При перенумерации (синтез, `restoreOrder`) обнови ссылки.

## Сценарии

```json
{
  "id": "SC2",
  "title": "Двойная выдача e1",
  "base": "SC1",
  "values": {
    "S1": [
      ["ann", "e1", 3],
      ["bob", "e1", 4]
    ]
  },
  "expect": [
    { "of": "A1", "holds": false },
    { "of": "D2", "contains": ["e2"], "excludes": ["e1"] },
    { "of": "F1", "args": ["ann"], "value": ["e1"] },
    { "expr": "card(D1)", "value": 1 }
  ]
}
```

- `values` — значения неопределяемых понятий **подписями**: `X#` / `C#` — массив подписей элементов; `S#` — по типизации: множество — массив, кортеж — массив компонент, элементы `Z` — числа. Индексы и `TUPLE_ID` не нужны.
- Понятия, не перечисленные в `values`, пусты. `base` наследует значения другого сценария; перечисленные здесь заменяют унаследованные целиком.
- `expect` — ожидания:
  - `of` — конституента: `D#` (значение), `A#` / `T#` (`holds`), `F#` / `P#` с `args` (аргументы подписями);
  - `expr` — выражение ЯРЭ над схемой (`card(D1)`, `D2⊆D1` с `holds`);
  - `value` — точное значение; `contains` / `excludes` — элементы, которые должны входить / не входить; `holds` — истинность.
- Порядок элементов в множествах не важен.

## Проверка

Из корня пакета rstool (в workspace Portal — `rsconcept/rstool`, в npm-проекте — `node_modules/@rsconcept/rstool`):

```bash
npx tsx skills/scripts/check-brief.ts --session <abs>/session.json --brief <abs>/brief.json [--base <abs>/v1-session.json] [--json]
```

В workspace Portal: `pnpm --filter @rsconcept/rstool exec tsx skills/scripts/check-brief.ts …`. Сессия — файл `exportSession`. Сценарии выполняются на копии сессии; сама сессия не меняется.

Скрипт печатает этап, покрытие, матрицу приёмки «сценарий × ожидание → факт», блокеры, предупреждения и следующий шаг. Код выхода `0` — блокеров нет, `1` — есть.

| Проверка                                                                                                        | Блокер когда                                                                         |
| :-------------------------------------------------------------------------------------------------------------- | :----------------------------------------------------------------------------------- |
| статус брифа                                                                                                    | `draft`                                                                              |
| требование без `via`                                                                                            | всегда (этап 2 не пройден)                                                           |
| требование без конституенты                                                                                     | всегда; причина — не хватает исходного понятия, понятие не выведено или нужен синтез |
| инвариант без аксиомы                                                                                           | всегда                                                                               |
| инвариант без позитива / негатива                                                                               | `project`; иначе предупреждение                                                      |
| сценарий не прошёл                                                                                              | всегда                                                                               |
| различение не подтверждено сценарием                                                                            | `research`; иначе предупреждение                                                     |
| пустая конвенция `X#` / `C#` / `S#`                                                                             | всегда                                                                               |
| диагностики с `severity: error`                                                                                 | всегда                                                                               |
| «сироты» — вне путей к требованиям и аксиомам                                                                   | `project`; иначе предупреждение                                                      |
| с `--base`: аксиома или конституента брифа удалена, производное стало неопределяемым, формула стала тривиальной | если имени нет в журнале решений                                                     |
| требование выражено `S#` без решения                                                                            | предупреждение                                                                       |

Чистый вывод не доказывает смысл схемы: он показывает только то, что записано в брифе. Полнота брифа — ответственность этапов 1–2.

## Лёгкий бриф

Для точечной правки (одна формула, одно понятие) достаточно: `status`, `approach`, `object`, `task`, одно требование с `via` и `constituent` и один сценарий. Объяснение формулы и вопросы по синтаксису обходятся без брифа.
