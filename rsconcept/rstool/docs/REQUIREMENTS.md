# Требования к ПО → бриф схемы

Как превратить ТЗ или запрос на изменение в требования к выразительным средствам, различения и инварианты брифа ([BRIEF.md](BRIEF.md)). Метод — [METHOD.md](METHOD.md). Выдержки — из примеров [`library-loans`](../examples/library-loans/NOTES.md), [`access-control`](../examples/access-control/NOTES.md), [`clinic-booking`](../examples/clinic-booking/NOTES.md).

Назначение такой схемы — `approach: project`: основа для модели данных и проверок. Строгость максимальная: у каждого инварианта позитивный и негативный сценарий, в сценариях — реальные объекты, «сироты» — ошибка.

## 1. Расчистка пунктов ТЗ

Каждый пункт — в одну из категорий:

| Вид пункта ТЗ                              | Пример                                                  | Куда                                                            |
| :----------------------------------------- | :------------------------------------------------------ | :-------------------------------------------------------------- |
| сущность или отношение                     | «экземпляр — копия одного издания»                      | ядро (этап 2) и, если есть «один», «каждый», — инвариант        |
| правило «не может», «не больше», «только»  | «экземпляр не выдан двоим», «не больше 5 на руках»      | инвариант → аксиома                                             |
| «система показывает / находит / считает …» | «показывает доступные экземпляры»                       | требование к выразительным средствам: **понятие**, а не функция |
| состояние, статус, вид                     | «первичная или повторная запись», «лекция или практика» | классификация: структуры и аксиомы разбиения, не коды `C#`      |
| время, история, журнал                     | «история выдач», «журнал изменений 3 года»              | обычно ограничение `restrictions` с невыразимым                 |
| оплата, уведомления, интеграции            | «SMS за сутки», «оплата онлайн»                         | ограничение (вне предметной области задачи)                     |
| интерфейс и качество                       | «удобный поиск», «выгрузка в Excel»                     | нерелевантно; в схему не идёт, в разметке отмечено              |
| процедура (кто что делает)                 | «председатель назначает рецензентов»                    | действие вне схемы состояния; роль — только если нужна правилам |

Пункт про действие («система показывает должников») превращается в понятие («должники»). Пункт про процедуру, если он задаёт ограничение («нельзя выдавать должнику»), — решение: аксиома состояния или «без аксиомы — правило процедуры» (`library-loans`, `DC6`).

## 2. Различения из ТЗ

Ищи пары, которые ТЗ называет одним словом или которые легко склеить при реализации:

- сущность и её экземпляр: **издание ≠ экземпляр**;
- назначенное и действующее: **назначенные права ≠ эффективные**, **прямая роль ≠ унаследованная**;
- план и факт: **запись ≠ приём**, **назначение ≠ написанная рецензия**;
- «есть свойство» и «доступно для действия»: **свободный слот ≠ доступный пациенту**;
- множество и подмножество по правилу: **читатели с выдачами ≠ должники**.

Для каждого различения — сценарий-свидетель, где значения различаются. Если свидетеля не придумать — возможно, различения нет.

## 3. Инварианты

- Формулировка из ТЗ, ссылка `ref`, будущая аксиома.
- Позитивный сценарий: нормальные данные, правило выполнено. Негативный: нарушено **только это** правило.
- Числа и пороги («не больше 5», «не больше двух продлений») — граничный сценарий на пороге и за ним.
- Правила «через» («в том числе через иерархию») — негатив именно на косвенный случай (`access-control`, `SC3`): иначе проверка только прямого случая выглядит «зелёной».

## 4. Типичные решения ядра для ПО

| Ситуация в ТЗ                                            | Решение                                                   | Пример                     |
| :------------------------------------------------------- | :-------------------------------------------------------- | :------------------------- |
| «у X один Y»                                             | отношение + аксиома однозначности, не функция в типе      | `library-loans` `A1`, `A3` |
| на объект ссылаются из нескольких мест                   | сущность `X#` с отношениями, а не кортеж                  | `clinic-booking` слот      |
| роли и иерархии                                          | одно множество и отношения; замыкание через `R{}`         | `access-control` `F1`      |
| текущее состояние без истории                            | структуры состояния + «текущий день» `S#: Z`              | `library-loans` `S3`       |
| производное значение («права пользователя», «просрочка») | вывод через `D#` / `F#`, не `S#` «задаётся вручную»       | `access-control` `DC2`     |
| запрос на изменение меняет смысл понятия                 | новое решение с `supersedes`; старые сценарии — регрессия | `library-loans` `DC8`      |
| новая информация к старой структуре                      | отдельная структура, не новая компонента кортежа          | `library-loans` `DC7`      |

## 5. Запрос на изменение (v2)

1. Восстанови бриф v1 (или возьми готовый) и сохрани сессию v1 как базу.
2. Спроси, что должно остаться неизменным (раунд 1).
3. Новые пункты — новые требования и инварианты; затронутые старые — новые решения с `supersedes`.
4. `check-brief --base <v1>`: удалённые и ослабленные понятия без нового решения — блокеры.
5. В отчёте — сводка изменений относительно v1.
