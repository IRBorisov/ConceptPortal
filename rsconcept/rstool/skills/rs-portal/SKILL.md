# Portal

Пути — от `<rstool>`. Указатель REST — `docs/PORTAL-API.md`.

## Ссылка → API

Из UI-ссылки `https://portal.acconcept.ru/rsforms/856?tab=editor` возьми тип объекта и ID `856`. Для метаданных и проверки прав используй `GET /api/agents/library/856/access`. Для полного JSON КС по этому ID используй `/details`. REST-хост и маршруты чтения указаны в `docs/PORTAL-READ.md`.

- С API-ключом пользователя: `/api/agents/...` и `Authorization: Bearer rcp_…`.
- При публичном чтении сразу выбирай анонимный маршрут. Для закрытой операции проверь, что нужный инструмент есть в каталоге HTTP MCP, затем вызови `portal_preflight(operation, audience, kind, targetId)`. Для метаданных и проверки доступа достаточно этой операции или `GET /api/agents/library/:id/access` в отдельно авторизованном REST-клиенте. Проверка записи требует `operation: write` либо `publish` для полной замены.
- Различай отказ HTTP-транспорта MCP, отсутствие инструмента и ответ `portal_preflight`. Если результат указывает на ключ или привязку, используй выданную инструментом `connectionPage` для нужного проекта или `nextAction` для OAuth. После смены подключения повтори проверку. При закрытом объекте и отсутствии подключения можно взять экспорт `/details` от владельца. Секреты остаются в хосте или в отдельно авторизованном клиенте.
- При `PORTAL_CONFLICT` перечитай редакцию и данные согласованной сводки. При `PORTAL_RATE_LIMITED` учти `retryAfter`. Коды и HTTP-маршруты описаны в `docs/PORTAL-READ.md`.

## Чтение и импорт

`portal_search_library` ищет доступные объекты, включая личные. `portal_get_details` читает КС, КМ или ОСС. Для публичной цели передай `audience: public`. Если нужны отдельные конституенты, для дальнейшей работы передавай их и зависимости. Полный ответ сохрани отдельно. В браузерной работе передавай снимки как изображения или ссылки на сохранённые файлы.

1. `GET …/rsforms/:id/details` → файл в папке задачи (UTF-8).
2. `importData(payload)` — `auto` распознает JSON Portal; не передавай его как `kind: 'session'`.
3. `listDiagnostics()`; дальше по маршруту (`skills/rstool/SKILL.md`): ревью, развитие.
4. Сохрани сессию-базу (`exportSession`) — для `check-brief --base` и сводки изменений.

Модели — `docs/PORTAL-MODELS.md`; ОСС — `docs/PORTAL-OSS.md`.

## Бриф на Portal

Пока бриф на Portal не хранится (план — блок «Задание» в паспорте схемы): держи `brief.json` в папке задачи. При ревью или развитии схемы Portal без брифа восстанови его (`rs-scope` §«Восстановление брифа»).

## Новая КС и путь

«Папка» библиотеки задаётся строкой `location` самой схемы. Отдельный объект папки или запрос на его создание не нужен. Например, для диплома D00B01 сразу задай `/U/Дипломы/D00B01`; несколько схем этой работы получают тот же путь и разные имена.

`portal_create_schema_from_session` создаёт объект и загружает содержимое одной операцией. Перед созданием покажи сводку и согласуй название, шифр, путь, видимость и источник. Передай `title`, `alias`, `location`, `accessPolicy` и устойчивый `requestId`. Для пустого объекта используй `portal_create_schema`. В отдельно авторизованном REST-клиенте этим вариантам соответствует `POST /api/agents/rsforms` с полем `schema` или без него. Передавай `Idempotency-Key`.

После потери ответа используй `portal_get_creation_status` с исходным `requestId`, затем перечитай объект и сверь ревизию, содержимое, владельца, путь и видимость. Если был создан пустой объект, продолжай на найденном ID через подготовленную публикацию. На старом адаптере при неопределённой локальной квитанции сначала найди объект через поиск. Порядок записи указан в `docs/PORTAL-PUBLISH.md` §«Новая КС».

`createSession` / `create_session` создаёт сессию rstool, а не объект Portal. Каталог конкретного MCP может предоставлять только часть REST API. Отсутствие инструмента создания КС в этом MCP не означает отсутствия операции на портале. При необходимости используй разрешённый REST-доступ; привязанный к MCP ключ не извлекай. Называй точную недостающую возможность или авторизацию, а не «создание папок».

## Замена существующей КС

Если задача требует сохранить ошибочные выражения источника, загружай их обычным способом и поясняй ошибки в комментариях соответствующих конституент или описании схемы. Диагностики не являются запретом публикации. После записи сверь результат повторного чтения.

Протокол — `docs/PORTAL-PUBLISH.md` §«Протокол публикации»:

1. Работа по этапам, пока `check-brief` не покажет этап `review` без блокеров (или пользователь согласился с «готово частично»).
2. Вызови `portal_prepare_publication` с `targetId`. Покажи цель, ожидаемую редакцию, исходную сессию, изменения метаданных и все изменившиеся обозначения. Если предварительный просмотр нового описания сокращён, уточни полный текст из исходной сессии. Дождись явного согласия на эту сводку.
3. В том же рабочем пространстве передай `publicationId` и `digest` в `portal_apply_publication`. Если черновик истёк или изменились источник, подключение либо цель, подготовь новую сводку и получи согласие ещё раз.
4. Сверь `verified`, версию и данные цели. Если ответ потерян, передай `publicationId` в `portal_get_publication_status`. Это можно сделать из другого чата с доступом к тому же проекту. Квитанция подтверждает факт записи, а `verified` показывает, совпадают ли текущая редакция и метаданные с квитанцией. Перечитай объект и укажи его ссылку в отчёте. На старых хостах проверь доступность согласованной записи через кабинет или отдельно авторизованный REST-клиент.

В настроенном HTTP MCP `portal_get_description(targetId)` читает описание и редакцию привязанным ключом без локальной сессии, в том числе для непубличной схемы. Для правки только комментария схемы используй CAS `/description` или `portal_update_description(targetId, expectedTimeUpdate, description)` настроенного HTTP MCP, см. `docs/PORTAL-PUBLISH.md` §«Только комментарий схемы». Полная замена и rstool-сессия для этого не нужны. Отдельное подтверждение каждой записи комментария на странице публикаций не требуется.

## Релятивизация

Выбери один из двух сценариев по задаче. В меню исходной КС «Редактирование» → «Релятивизация» сохраняет самостоятельный результат. На графе ОСС «Добавить…» → «Релятивизация» создаёт связанный результат для последующих сквозных изменений. Сессионные маршруты обоих сценариев описаны в [PORTAL-OSS.md](../../docs/PORTAL-OSS.md#релятивизация-в-portal).

В сводке называй исходную КС, релятивизируемую конституенту и исключения. Объясни, что считается одним контекстом. После выполнения операции проверь формулы и термины в КС результата. Нужные правки терминов, текстовых определений и конвенций вноси в открывшуюся КС. Термины бери из [DOMAIN.md](../../docs/DOMAIN.md#релятивизация).

## Расположение и доступ

Путь новой КС задаётся при создании. Для уже существующей владелец или staff меняет `location` и `access_policy` ключом: `PATCH /api/agents/library/:id/set-location` и `set-access-policy`. Редактор эти поля не меняет. В `/L` пишет только staff. Обычный `PATCH /api/library/:id/set-location` ключ не открывает. Подробно — `docs/PORTAL-PUBLISH.md` §«Расположение и политика доступа». Не переноси существующую схему без просьбы пользователя.

## Лимиты

Правки: 30 в минуту, 300 в час; `replace`, `create-version` и создание КС — ещё не больше 15 в час. `429` — бюджет кончился, не повторяй в цикле. Подробно — `docs/PORTAL-PUBLISH.md` §«Лимиты».

## Не делай

- Публикуй после явного согласия пользователя на показанную сводку.
- Не предлагай авторизацию через session cookie.
- Не перебирай id подряд — используй контекстный поиск.
