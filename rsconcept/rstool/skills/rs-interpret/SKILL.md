# Этап 4 · Интерпретация

Пути — от `<rstool>`. Формат сценариев — `docs/BRIEF.md` §«Сценарии»; формы значений КМ и тесты — `docs/MODEL-TESTING.md`.

## Вход

Схема без ошибок диагностик (сессия, сохранённая `exportSession`) и `brief.json` со сценариями.

## Шаги

1. **Ожидания на конституенты.** В каждый сценарий допиши `expect`: для требований — `value` или `contains` / `excludes` на их конституенты; для `F#` / `P#` — `args` подписями; для инвариантов — `holds` на аксиому. Ожидания выводи из смысла требования и источника, **не** из того, что вычисляет текущая формула.
2. **Покрытие сценариями.**
   - У каждого инварианта — `positive` (аксиома истинна) и `negative` (ложна). Негатив нарушает ровно это правило, иначе он ничего не доказывает.
   - У каждого различения — `witness`: сценарий, где значения двух понятий различаются.
   - При развитии схемы старые сценарии остаются — это регрессия.
   - Граничные случаи там, где в требовании есть число или порог (`≥ 3`, `≤ 20`): ровно на границе и за ней.
3. **Прогон.**

   ```bash
   npx tsx <rstool>/skills/scripts/check-brief.ts --session <abs>/session.json --brief <abs>/brief.json
   ```

   В workspace Portal: `pnpm --filter @rsconcept/rstool exec tsx skills/scripts/check-brief.ts …`. Сценарии выполняются на копии сессии — рабочая модель не портится. Матрица приёмки: сценарий × ожидание → факт.

4. **Разбор провала.** Прежде чем менять формулу, ответь, где ошибка:
   - **в ожидании** (неправильно понят источник) — уточни у пользователя или в источнике, исправь сценарий и запиши почему;
   - **в формуле** при верном ядре — `rs-explicate`, правка без изменения смысла требования;
   - **в ядре** (понятие не выражается, различение склеилось, вид вместо рода) — вернись в `rs-core`, новая гипотеза и запись в журнал решений.

   Менять ожидание под результат формулы без такого разбора — подгонка.

5. Повторяй прогон, пока блокеров `interpret` нет.

## Выход

Сценарии с ожиданиями в `brief.json`; вывод `check-brief` с матрицей приёмки — в отчёт.

## Гейт

- Все сценарии проходят.
- У каждого инварианта есть позитивный и негативный сценарий.
- Каждое различение подтверждено сценарием, на котором значения различаются. Предупреждение «различение не проверено» — не сдавать: добавь сценарий с `expr`, на котором значения различаются, или скажи в отчёте, что различение не проверено.

Дальше — `rs-review`. При провале — `rs-core` или `rs-explicate` по шагу 4.

## Не делай

- Не проверяй только «нет диагностик» или только позитивные данные.
- Не пиши ожидание, подсмотрев значение формулы.
- Не добавляй в рабочую схему конституенты «для теста» — используй `expr` в сценарии.
- Не задавай значения производным понятиям: только `X#`, `C#`, `S#`.

## Если скрипт не подходит

Сложная проверка (перебор по `Z`, функции с радикалами) — вручную на копии сессии: `setModelValues` и `evaluate` (`docs/MODEL-TESTING.md`, `skills/rstool-runtime/SKILL.md`). Результат всё равно запиши сценарием в бриф, если ожидание выражается.
