# Этап 3 · Экспликация

Пути — от `<rstool>`. Проектирование формул — `docs/CONCEPTUAL-SCHEMA.md`; синтаксис — `docs/SYNTAX.md`; коды диагностик — `docs/DIAGNOSTICS.md`; вызовы — `skills/rstool-runtime/SKILL.md`.

## Вход

Бриф с `via` у каждого требования и решениями по ядру. Для починки формулы — лёгкий бриф: смысл конституенты одной строкой (из термина, текстового определения или вопроса пользователю) и сценарий, который этот смысл проверяет. **Смысл фиксируется до правки.**

## Шаги

1. **Ядро.** `X#`, `C#`, `S#` с предметными конвенциями: что элемент, порядок компонент кортежа, ссылка на решение (`DC#`). Затем аксиомы из решений по свойствам.
2. **Развёртывание от требований.** Для каждого требования по его `via` — конституента и только нужные поставщики. Не выводи все возможные термы.
   - Раскрытие структуры: `D# := Pr1(S1)`, `Pr2,3(S1)`, `red(…)` — термины для компонент.
   - Обособление: выражение со свободной переменной — `F#` / `P#`; повторяющийся фрагмент — `D#` / `F#`.
   - Зависимость «аргумент → значение» — `F# ::= [ξ∈A] E(ξ)`, не множество пар `I{(ξ,σ) | …}`.
   - (Не)пустота — `S ≠ ∅` / `S = ∅`, не `card(S) > 0`.
   - Транзитивное замыкание, достижимость, ацикличность — через `R{}` в `F#`, а не квантор по `ℬ(X1)` (`invalidPropertyUsage`).
   - Однозначность отношения — `card(S1)=card(Pr1(S1))`.
3. **Порядок:** `X#`, `C#` → независимые `S#` → `D#`/`F#`/`P#` → `A#`/`T#`; поставщики раньше потребителей (`applySchemaPatch` упорядочивает пачку сам).
4. **Перед сохранением** сомнительной формулы — `analyzeExpression`. Пачку правь одним `applySchemaPatch`.
5. **Ссылки брифа.** Впиши в `expressiveness[].constituent` и `invariants[].constituent` имена конституент. Сохрани сессию (`exportSession`) в папку задачи.
6. **Проверка:** `check-brief` (`docs/BRIEF.md`). Блокеров `core` и `explicate` быть не должно; дальше — `rs-interpret`.

## Цикл диагностик

1. `listDiagnostics()`: `kind` — `expression` (формула), `schema` (омонимы, дубликаты, конвенции), `model` (интерпретация).
2. По `name` найди исправление в `docs/DIAGNOSTICS.md`; короткие «было → стало» — `skills/rstool-runtime/EXAMPLES.md` «Типичные диагностики». Для ошибок внутри `F#`/`P#` смотри `stack[0]`.
3. Исправляй диапазон `from`–`to` в формуле так, чтобы **смысл из брифа сохранился**; проверь сценарием.
4. Не повторяй вызов без изменения ввода.

## Смысл важнее «зелёного»

Нельзя ради чистых диагностик:

- удалять или ослаблять аксиому, связанную с инвариантом брифа, без нового решения в журнале;
- превращать производное понятие (`D#`/`F#`/`P#`) в `S#`, `X#` или `C#` — у неопределяемого нет формулы, поэтому нет и ошибок, но понятие перестаёт выводиться;
- заменять формулу тривиальной (`∅`, `D5 := X1`, тавтология) или менять порог / условие (`≥ 2` → `≥ 1`);
- удалять конституенту, на которую ссылается бриф, или оставлять непустой `failed` после `best_effort`;
- оставлять пустую конвенцию у неопределяемого понятия.

Если смысл не выражается: вернись в `rs-core` (другая гипотеза ядра, промежуточные `D#`/`F#`) и запиши решение. Если ЯРЭ этого не выражает — `openQuestions` в бриф и честное «готово частично» в отчёте. При развитии схемы запускай `check-brief` с `--base <прежняя сессия>`: он ловит удалённые и ослабленные понятия.

## Выход

Сессия в папке задачи; бриф со ссылками на конституенты.

## Гейт

- Диагностики чисты, `failed` пуст.
- У каждого требования и инварианта есть конституента; ни одно не ослаблено.
- Конвенции у всех `X#` / `C#` / `S#`.
- Описание схемы (`comment` сессии, на Portal — описание) содержит назначение, ограничения с невыразимым и краткий журнал решений; конвенции не ссылаются на `DC#`, которых там нет. Бриф пока не уходит в Portal — без этого решения теряются при экспорте. Для `education` текст решений в схеме обязателен.

## Не делай

- Не вводи `S#` для отношения, которое выводится из других.
- Не кодируй атрибуты и статусы константами `C#`.
- Не добавляй `R1` как конституенту: радикал живёт только в `[…]` у `F#` / `P#`.
- Не правь пакет `<rstool>` — скрипты и сессии в папке задачи.
