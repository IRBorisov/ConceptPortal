1. Исходные решения

Зафиксированы по ответам на вопросы перед составлением плана:

  • Главные симптомы: (а) запрос не покрыт: в схеме нет понятий и утверждений, ради которых её просили; (б) подгонка под «зелёное»: агент упрощает формулы, удаляет аксиомы или подменяет производные понятия родовыми структурами, чтобы ушли ошибки.
  • Типичные задачи: КС по тексту (источник, требования) и развитие существующей КС из Portal.
  • Назначение КС: экспликация понятий, обучение, основа для ПО и ОСС. Вычисления на КМ здесь средство проверки смысла, а не самоцель.
  • Вопросы пользователю: короткий бриф: 3–5 вопросов и подтверждение брифа до формализации. Всё, что не спросили, записывается как явное допущение.
  • Объём изменений: допустимы любые, включая архитектуру, API rstool, backend и UI Portal.
  • Бриф хранится в сессии rstool и на Portal рядом со схемой.
  • Новые примеры: требования к ПО.
  • Eval: реальных неудачных случаев нет, поэтому набор задач с эталонами составляем с нуля.

2. Диагноз: почему «зелёная» ≠ «нужная»

Ниже причины, найденные в текущих скиллах и документации. Каждая подкреплена конкретным местом в коде или тексте.

D1. Критерий готовности только формальный

Шаблон ответа «Сборка / правка схемы» в GUIDE.md спрашивает лишь, «есть ли активные диагностики» и какие проверки выполнены. Канонические примеры заканчиваются assertCleanDiagnostics. Цель, которую агент видит, — ноль диагностик.

D2. Нет этапа постановки задачи

Концептуализация начинается со слов «Собери словарь…» и сразу переходит к X#/S#. Цель схемы, целевые понятия, различения и границы нигде не фиксируются. «Предметная редукция» описана как принцип, но без процедуры.

D3. Нет трассировки «запрос → конституента»

Схема строится снизу вверх: от словаря к производным понятиям. Целевые понятия никак не отмечены. Термины «ядро» и «тело» есть в DOMAIN.md, но в процессе не используются. Флаг crucial Portal rstool не поддерживает.

D4. Проверка смысла необязательна

КМ включается только «при сомнении». Тесты проверяют формулу, а не то, отвечает ли схема на вопрос пользователя. Шаг громоздкий: индексы, TUPLE_ID, id конституент. Агенты его пропускают.

D5. Цикл диагностик поощряет подгонку

В «Цикле диагностик» нет запрета менять смысл. Самый дешёвый способ убрать ошибку — объявить S#: у него нет формулы, значит, нет и ошибок. Ещё варианты — удалить A# или выбрать best_effort и забыть про failed. Инструмент ничего из этого не замечает.

D6. Монолитный гайд без понятия «этап»

GUIDE.md (306 строк) смешивает методологию, язык ЯРЭ, механику запуска скриптов, Portal REST и ревью. Описание скилла перечисляет всё подряд. Агент держит в контексте лишнее и не понимает, где он сейчас и что дальше. Состояния процесса между итерациями нет.

Дополнительно: есть две вручную расходящиеся копии SKILL.md (пакет и .agents/skills/). Чек-лист ревью почти целиком про форму ЯРЭ: пункт «покрыты главные сущности» один, и метода проверки у него нет. Ревью Portal-схемы не восстанавливает, для чего схема делалась.

3. Принципы переработки

  1. Готово = отвечает брифу. Схема готова, когда покрыты целевые понятия, различения и инварианты из брифа, это подтверждено примерами на КМ и диагностики чисты. Чистые диагностики — необходимое условие, но не достаточное.
  2. Сверху вниз от цели. Проектирование начинается с целевых понятий брифа: от них выводится, какие неопределяемые понятия нужны. Так покрытие встроено в процесс, а пересказ источника отсекается.
  3. Смысл важнее «зелёного». Исправление диагностики не должно менять смысл. Если сохранить смысл не удаётся, агент возвращается к проектированию или фиксирует открытый вопрос, но не подменяет формулу.
  4. Инструмент знает этап. rstool вычисляет готовность (readiness) и подсказывает следующий шаг. Агенту не нужно держать процесс в голове.
  5. Один скилл — один этап или инструмент. Скилл загружает только нужный контекст, у каждого есть вход, выход и гейт.
  6. Примеры — главный учебный материал. Каждый эталонный пример содержит бриф, сценарии и «антипример»: зелёную, но неверную схему с объяснением, какая проверка её ловит.

5. Бриф схемы

Бриф — один формат JSON, общий для файла задачи, сессии rstool и Portal. На этапе 1 агент задаёт 3–5 вопросов, заполняет бриф и показывает пользователю короткую версию для подтверждения.

Вопросы постановки (выбрать 3–5 по ситуации)

  1. Для чего будет использоваться схема: экспликация, обучение или основа для ПО / синтеза?
  2. Какие понятия обязательно должны получить определение? Что пользователь хочет «уметь различать»?
  3. Какие правила или ограничения схема должна выражать (инварианты)?
  4. Что сознательно оставить за рамками?
  5. Приведите 1–2 конкретные ситуации (пример и контрпример) для главного понятия.
  6. (Для Portal) Что меняется относительно текущей версии схемы и что должно остаться неизменным?

Каждый вопрос агент задаёт вместе со своим предложенным ответом, взятым из источника, чтобы пользователь мог просто подтвердить. Если спросить нельзя (фоновый агент), ответы записываются в assumptions, а статус брифа становится assumed.

Структура (пример: требования к ИС библиотеки)

{
  "version": 1,
  "status": "confirmed",              // draft | assumed | confirmed
  "purpose": "software",              // explication | education | software
  "goal": "Эксплицировать понятия выдачи книг для проектирования ИС библиотеки",
  "source": "ТЗ v1, разделы 2–3",
  "scope": {
    "in":  ["выдача и возврат экземпляров", "просрочка", "лимит выдач"],
    "out": ["штрафы", "межбиблиотечный абонемент"]
  },
  "targets": [
    { "id": "T1", "concept": "активная выдача",    "ref": "ТЗ 2.1", "constituent": "D3" },
    { "id": "T2", "concept": "просроченная выдача", "ref": "ТЗ 2.4", "constituent": "D5" },
    { "id": "T3", "concept": "доступный экземпляр", "ref": "ТЗ 3.1", "constituent": null }
  ],
  "distinctions": [
    { "id": "R1", "between": ["издание", "экземпляр"], "witness": "SC2" },
    { "id": "R2", "between": ["T1", "T2"],             "witness": "SC2" }
  ],
  "invariants": [
    { "id": "I1", "text": "Экземпляр не выдан двум читателям одновременно",
      "constituent": "A1", "positive": "SC1", "negative": "SC3" }
  ],
  "scenarios": [
    { "id": "SC1", "title": "Две обычные выдачи",
      "values": { "X1": ["ann", "bob"], "X2": ["e1", "e2"],
                  "S1": [["ann", "e1", 3], ["bob", "e2", 5]] },
      "expect": [ { "of": "D5", "value": [] }, { "of": "A1", "holds": true } ] },
    { "id": "SC3", "title": "Двойная выдача e1",
      "values": { "S1": [["ann", "e1", 3], ["bob", "e1", 4]] },
      "expect": [ { "of": "A1", "holds": false } ] }

  • В сценариях значения задаются подписями элементов, а не индексами: инструмент сам переводит их в индексы. Это снимает главный барьер для КМ-проверок (D4).
  • Цели ссылаются на конституенты по имени. Внутри хранится id, чтобы ссылка переживала перенумерацию при синтезе.
  • constituent: null означает, что цель ещё не покрыта. Это видно в readiness и в UI.

Вложенное размещение (rsconcept/rstool/.claude/skills/, rsconcept/rstool/.agents/skills/) срабатывает по месту файлов, а не по запросу. Типичная задача — «построй КС по тексту» или «доработай схему по ссылке» — вообще не трогает файлы пакета, поэтому скилл не всплывёт именно тогда, когда нужен. Для npm-пользователей ни один хост не сканирует node_modules.

Решение: регистрируется одна точка входа, всё остальное читается по пути.

  1. Одна строка маршрутизации в корневом AGENTS.md: «Работа с КС, ЯРЭ, rstool или Portal → прочитай rsconcept/rstool/skills/rstool/SKILL.md». AGENTS.md всегда в контексте у Codex и Cursor. Для Claude Code добавить CLAUDE.md с одной строкой @AGENTS.md. Работает без регистрации скиллов, на любой ОС.
  2. Заглушки для автосрабатывания — .claude/skills/rstool/SKILL.md и .agents/skills/rstool/SKILL.md: только name, description и указание «прочитай rsconcept/rstool/skills/rstool/SKILL.md». Содержимого нет, поэтому синхронизировать нечего. Тест проверяет, что description совпадает с исходником. Если Cursor покажет дубль (он читает обе папки), оставить одну заглушку в .agents/skills/.
  3. Скиллы этапов не регистрируются. Маршрутизатор и readiness.next называют этап, агент читает skills/rs-…/SKILL.md по пути. Скиллы этапов не конкурируют за срабатывание, и в списке скиллов хоста нет девяти похожих описаний.
  4. Пути внутри скиллов пишутся от корня пакета с явным правилом: <rstool> — это rsconcept/rstool/ в workspace Portal или node_modules/@rsconcept/rstool/ в npm-проекте. Один и тот же файл работает в обоих местах, переписывать пути скриптом не нужно.

Симлинки (.claude/skills/rstool → ../../rsconcept/rstool/skills/rstool) отклонены: на Windows без core.symlinks и режима разработчика git создаёт вместо ссылки текстовый файл, а основная работа ведётся на Windows.

Для npm-пользователей

  • Bin rstool-skills install [--dir …] пишет ту же заглушку с путём в node_modules/@rsconcept/rstool/, а не копирует содержимое. После обновления пакета переустанавливать ничего не нужно.
  • MCP prompts и resources в rstool-mcp (фаза 5) — путь без файлов вообще: клиент получает этапы и справочники с сервера.
  • Вариант на будущее: плагин Claude Code / Cursor, который ставит заглушку и MCP-сервер одной командой.

Совместимость: rstool-helper остаётся заглушкой «используй rstool» на один минорный релиз, затем удаляется. GUIDE.md превращается в указатель на новые скиллы.

7. Защита от «озеленения»

Правила (в rs-formalize, rs-review и маршрутизаторе)

Нельзя ради чистых диагностик:

  • удалять или ослаблять аксиому, связанную с инвариантом брифа;
  • превращать производное понятие (D#/F#/P#) в S#, X# или C#;
  • заменять формулу тривиальной (∅, голая ссылка D5 := X1, тавтология);
  • удалять целевую конституенту или оставлять непустой failed после best_effort;
  • оставлять пустую конвенцию у неопределяемого понятия.

Вместо этого: если не удаётся выразить смысл, вернись к проектированию (другие неопределяемые понятия, промежуточные D#/F#). Если ЯРЭ этого не выражает — запиши openQuestion в бриф и сообщи пользователю. Отчёт тогда честно говорит «готово частично» и перечисляет, что именно не покрыто.

9. Portal: бриф рядом со схемой

Backend

  • Модель SchemaBrief (OneToOne к LibraryItem, data: JSONField, time_update) в apps.rsform.
  • GET/PUT /api/rsforms/:id/brief и /api/agents/rsforms/:id/brief (журнал мутаций, лимиты, X-Expected-Time-Update).
  • Бриф включается в /details, в снимок версии, в load-json и replace, копируется при клонировании.
  • Валидация структуры на сервере (JSON-схема), без логики покрытия.

Frontend

  • Отдельной вкладки нет: бриф выводится блоком «Задание» внизу паспорта (tab-schema-card), под формой схемы и редактором атрибутов, на всю ширину вкладки.
  • Состав блока: цель и назначение, затем сворачиваемые подразделы: цели с состоянием покрытия, различения, инварианты, сценарии (прогон в браузере через RSEngine), допущения, открытые вопросы.
  • Блок сохраняется отдельно от формы паспорта, через PUT …/brief, со своим признаком изменений. Если брифа нет, вместо блока показывается компактная заглушка «Задание не задано».
  • В боковую статистику (ViewSchemaStats) добавить строки покрытия: цели, инварианты, сценарии.
  • Значок «цель T1» на конституенте и фильтр «цели» в списке.
  • Тексты через useTx/globalTx, синхронно в en/ru/fr.

Протокол публикации (скилл rs-portal)

  1. /details → importData (бриф приходит вместе со схемой).
  2. Работа по этапам, пока readiness.stage = done.
  3. diffSessions: показать пользователю сводку и получить подтверждение.
  4. create-version (если есть права), затем replace с X-Expected-Time-Update.
  5. Повторно прочитать /details, импортировать и сверить. Отчёт со ссылкой.

ОСС

При синтезе бриф результата по умолчанию пустой. Агент может собрать его из брифов аргументов: цели переносятся по таблице отождествлений. Решение — в открытых вопросах.

Расширить X-Expected-Time-Update на replace и правки конституент, если поддержки там ещё нет: сейчас документирована только для моделей.

11. Проверка эффекта (eval)

Набор задач составляется с нуля и не пересекается с примерами: другие предметные области, иначе агент просто воспроизведёт эталон.

Тип задачиКол-во (v0 → v1)Что даётся агентуЛовушка
КС по требованиям2 → 4текст требований; ответы «пользователя» на вопросы постановкипересказ текста без целевых понятий
Развить КС2 → 3сессия v1 (с брифом или без) + запрос на изменениесломать старые сценарии; потерять инвариант
Ревью КС1 → 3зелёная схема с заложенными дефектамиотчитаться «диагностик нет — всё хорошо»
Починить формулу1 → 2схема с ошибкой, которую проще всего «исправить» ослаблениемподгонка под зелёное

Метрики и процедура

  • Автоматические: доля покрытых эталонных целей (агент сообщает соответствие в брифе), доля пройденных скрытых эталонных сценариев на соответствующих конституентах, число нарушений из §7 (по diffSessions с базой), чистота диагностик.
  • Оценка моделью-судьёй: качество вопросов постановки (релевантность, наличие предложенных ответов, число), честность отчёта о готовности.
  • Стоимость: токены, время, число вызовов инструментов.
  • Прогон: headless-агент + симулятор пользователя, который отвечает по карточке задачи. Три прогона на задачу, усреднение. Базовый прогон делается на текущем rstool-helper до любых изменений, затем после каждой фазы.
  • Отдельный тест срабатывания скиллов: 30 формулировок запросов → ожидаемый скилл.
  • Расположение: rsconcept/rstool/evals/ (не входит в files npm-пакета).

13. Риски и открытые вопросы

Риск / вопросПредложение
Бриф — лишняя работа на мелких задачах«Лёгкий» бриф: для точечной правки достаточно одной цели и одного сценария. Объяснение и вопросы по синтаксису обходятся без брифа. Маршрутизатор решает это по сценарию.
Девять скиллов конфликтуют при срабатыванииРегистрируется только маршрутизатор, скиллы этапов читаются по пути (§6). Тест срабатывания в eval проверяет одну точку входа.
Пользователь устаёт от вопросовНе больше 5 вопросов, у каждого предложенный ответ, одно подтверждение брифа целиком. Новые вопросы — только при появлении нового различения.
Фоновый агент не может спроситьСтатус assumed, допущения и открытые вопросы в отчёте. На Portal бриф помечен как неподтверждённый.
Ссылки брифа ломаются при синтезе и перенумерацииХранить id и показывать имя. synthesize обновляет ссылки по idMap.
Бриф при синтезе ОССОткрыто: пустой по умолчанию или собирать из аргументов по таблице отождествлений?
Кто подтверждает бриф на PortalОткрыто: поле confirmed_by или только статус. Нужна ли история изменений брифа отдельно от версий схемы?
Пороговые значения по назначению схемыОткрыто: считать ли «сирот» ошибкой для учебных схем? Пока предупреждение.
