Procurement eligibility checker

Decide whether a purchase request is allowed given vendor status, category policy, and approval thresholds — expressed as a conceptual schema (КС) in ЯРЭ, published in Concept Portal, and checked on small conceptual models (КМ).

Business purpose

Replace ad-hoc spreadsheet rules with an auditable eligibility definition: who may buy what, from which vendors, under which limits.

Actors: Procurement officer, category owner, finance approver, vendor master data steward.

Why ЯРЭ + Concept Portal

  • Eligibility is a predicate over relations (vendor↔category, request↔amount, role↔threshold) — natural fit for S#, F#, P#.
  • Policy changes become schema edits, not code forks; Portal versions preserve history.
  • Small КМ samples prove edge cases (blocked vendor, over-limit amount) before go-live.

Concept Portal usage

  • Publish КС Biz/ProcurementEligibility as a public or project library item.
  • Keep vendor–category approvals as model values or a sibling schema loaded via ОСС synthesize.
  • Export Portal details → rstool importData for agent-assisted policy edits; push back via exportPortal({ kind: 'schema' }).

rstool-helper delivery workflow

  1. Dictionary: requests, vendors, categories, roles, thresholds.
  2. Build core with applySchemaPatch; analyzeExpression before each formula.
  3. Smoke КМ: 3 requests (ok / blocked vendor / over limit); setModelValues + evaluate.
  4. Review checklist: no extra S# for computable relations; prefer F# for «for request → roles».
  5. Commit step; publish to Portal; document convention texts in business language.

Tooling loop

ensureSession → applySchemaPatch (core X/C/S)
analyzeExpression → patch D/F/P/A/T
setModelValues → evaluate / recalculateModel
listDiagnostics → fix → commitStep
exportPortal({ kind: 'schema' | 'model' }) → Portal library

MVP roadmap

  1. Single-category eligibility + amount threshold
  2. Multi-category vendor approval matrix
  3. ОСС: separate VendorMaster schema synthesized into policy schema
  4. UI/API consumer: evaluate P1/T1 for a request id

Risks & reductions

  • Encoding status as C# codes instead of relations — prefer S# for approvals.
  • Mixing ERP ids into formulas — keep ids in interpretation, not in ЯРЭ terms.

Success criteria

Schema ready

No expression/schema diagnostics; conventions in business language; review checklist passed.

Operations adopted

At least one consumer evaluates the key predicate/statement on real sample data; Portal version pinned in the runbook.
