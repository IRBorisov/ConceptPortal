Planning · Portal

Agents API, API keys & action log

Dedicated /api/agents surface for machine clients (rstool / MCP / scripts), authenticated by user-issued API keys. Keys do not unlock existing session/CSRF UI routes. Profile gains tabs for keys and an agent action log. No OSS actions in v1.

Decisions (locked)

Auth boundary A

API keys authenticate only /api/agents/*. Existing /api/rsforms, /api/library, etc. stay session + CSRF.

Key power A

Key acts as the issuing user (same Owner/Editor read/edit rules). Label + revoke only; no scopes / item binding in v1.

Mutation shape C

Hybrid: bulk replace (load-json / exportPortal payload) + curated granular constituenta actions. Portal-native bodies; reuse existing rsform services.

Scope & roadmap

v1: RSForm only (read library helpers + schema mutations). No OSS. Long-term: agents read/write Portal as source of truth instead of long-lived rstool sessions. Models later.

Current gap

  • Backend auth is session-only; anonymous REST sees public library only.
  • Agents today: read public JSON → edit in rstool → user pastes/loads exportPortal in UI.
  • No API key model, no agent audit trail, profile is name/email + password only.

Architecture

apps/agents/                    # new Django app
  models/
    ApiKey.py                   # hashed secret, prefix, label, owner, last_used
    AgentActionLog.py           # per-request audit for /api/agents writes (+ optional reads)
  authentication.py             # Bearer API-key auth (agents routes only)
  permissions.py                # IsAuthenticated via key or session (key mgmt = session)
  views/
    keys.py                     # CRUD keys — session auth only
    logs.py                     # list own action log — session auth only
    library.py                  # active / context-search / by-ids — API key
    rsforms.py                  # details, create, replace, granular — API key
  services/
    audit.py                    # write AgentActionLog
    rsform_ops.py               # thin wrappers calling existing rsform serializers/services

Frontend profile (/profile)
  Tabs: Account | API keys | Agent activity
  Account = existing profile + password
  API keys = create (show secret once) / list / revoke
  Agent activity = paginated action log

Wire format for agent mutations = existing Portal serializers
(rstool exportPortal schema JSON ↔ replace; CstCreate / update payloads for granular)

API surface (v1)

Session-auth (profile / SPA)

Method Path Purpose
GET /api/agents/keys List own keys (id, label, prefix, created, last_used; never secret)

DELETE /api/agents/keys/{id} Revoke / delete key
PATCH /api/agents/keys/{id} Rename label (optional)

Method Path Notes

API keys

  • Format: rcp_ + public prefix (8 chars) + _ + secret (32+ random). Store SHA-256 of full token only; return plaintext once on create.
  • Header: Authorization: Bearer rcp_…
  • On successful auth, update last_used_at (throttled write ok).
  • Revoke = delete row (or soft-delete flag); revoked keys fail auth immediately.
  • CSRF: not required for Bearer API-key requests on agent routes.

Action log

  • Fields: user, api_key (nullable FK / label snapshot), action (string code), item_id (nullable), item_alias / title snapshot, status_code, summary (short human text), created_at. No full request/response bodies in v1.
  • Log all mutating agent routes; optionally skip high-volume GETs or log only failures.
  • Profile “Agent activity” lists newest first; filter by key / action; pagination (~50).
  • Retention: keep indefinitely for v1 (add prune job later if needed).

Frontend profile

  • Refactor /profile to tabs: Account | API keys | Agent activity.
  • Reuse existing Tabs / TabLabel components.
  • API module under features/users/backend/ or new features/agents/ — prefer features/agents for keys/logs API + profile panels; profile page composes them.
  • i18n: en / ru / fr for all new copy.
  • Create-key UX: modal shows secret once with copy; warn it cannot be retrieved again.

Security & permissions

  • Agent views: ApiKeyAuthentication required (reject session-only on agent data routes, or allow both for debugging — prefer key-only for /api/agents/rsforms|library so audit always ties to a key).
  • Key CRUD + logs: session auth only (never API key managing keys).
  • Object permissions: reuse can_read_library_item / can_edit_item / ItemEditor / owner rules for create-version.
  • Throttle agent writes (new DRF throttle rate, e.g. agents: 60/minute).

Implementation order

  1. 1 Backend app skeleton: models, migration, ApiKeyAuthentication, key CRUD + logs list (session).
  2. 2 Agent library + rsform routes wrapping existing services; audit middleware / decorator on mutations.
  3. 3 Tests: auth, permissions, replace, granular create/update/delete, log entries.
  4. 4 Frontend profile tabs + keys UI + activity list + i18n.
  5. 5 PORTAL-API.md + OpenAPI smoke.

Non-goals (v1)

  • OSS / RSModel agent endpoints
  • Key scopes or item-bound keys
  • Unlocking existing UI routes with Bearer tokens
  • Shipping Portal HTTP client inside @rsconcept/rstool (docs + curl only for now)
  • Optimistic concurrency / If-Match (revisit when concurrent agent+UI edits hurt)

Success criteria

  • Agent with a user key can search private library, pull details, granular-edit or replace, and create a version — without browser cookies.
  • User can issue/revoke keys and see agent mutations in profile.
  • Session-only clients cannot call agent data routes; keys cannot call UI mutation routes.
