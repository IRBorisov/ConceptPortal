Role–resource access control matrix

Formalize which roles may perform which actions on which resources. Use ЯРЭ predicates as the source of truth for allow/deny, with Concept Portal as the shared policy library.

Business purpose

Give security and product teams one conceptual definition of authorization instead of duplicated ACL tables across services.

Actors: Security architect, app owners, compliance auditor.

Why ЯРЭ + Concept Portal

  • Access is relational: subject–role, role–permission, resource–action.
  • Derived terms answer «may subject do action on resource?» without procedural code.
  • Portal library + versions support review and rollback of policy changes.

Conceptual core (sketch)

Производные / проверки

AliasIntent

F1Permissions of a subject via roles

Aliases are a starting sketch for conceptualization — refine with BASE-SELECTION and avoid new X#/C#/S# when a D#/F#/P# suffices.

Concept Portal usage

  • КС Biz/AccessMatrix; optional OSS combining OrgRoles + ResourceCatalog schemas.
  • Auditors read Portal UI; agents pull /api/rsforms/:id/details when public.
  • Model instances per environment (dev/stage/prod) as separate КМ or value sets.

rstool-helper delivery workflow

  1. Reduce to one question: allow(subject, action, resource).
  2. Introduce S1/S2 first; add hierarchy S3 only if inheritance is required.
  3. Implement F1/P1; test with conflicting role grants.
  4. Portal publish; link from runbooks; no silent ACL drift in apps.

MVP roadmap

  1. Flat roles, no hierarchy
  2. Resource hierarchy inheritance
  3. Break-glass role with explicit axiom marking
  4. Export allow-set snapshot for gateway config

Risks & reductions

  • Encoding allow as boolean attributes on C# — loses composition.
  • Putting environment-specific subjects into the schema core — keep in КМ.

Success criteria
