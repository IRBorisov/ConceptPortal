#1 · P1

Обрыв сети записывает в сессию анонимного пользователя

воспроизведено

rsconcept/frontend/src/features/auth/backend/api.ts:85

return anonymousCurrentUser;

Уверенность: точно. Категория: Проглатывание ошибок.

Сценарий. В кеш запроса /users/api/auth положить пользователя с id 7. Три раза подряд GET завершается AxiosError без response. Вызвать fetchQuery со staleTime: 0.

Ожидаемое и фактическое. Ожидается сохранённый id 7 или ошибка запроса, по которой вызывающий код видит сбой. Фактически запрос успешно возвращает anonymousCurrentUser, и в кеше оказывается id: null.

Причина. После третьей сетевой ошибки функция возвращает анонимный объект, а не пробрасывает ошибку. Для TanStack Query это успешные данные. У запроса refetchOnWindowFocus: 'always' и staleTime в сутки, поэтому один неудачный refetch при фокусе окна заменяет вошедшего пользователя до следующего фокуса или восстановления сети.

Ущерб и условия. RequireAuth при id === null убирает детей. Несохранённый профиль, шаблоны промптов и форма создания элемента при этом разбираются. Редактор схемы через useAdjustRole получает роль читателя, пока сессионная cookie на сервере может оставаться действительной. Условие обычное: фокус окна во время короткого обрыва сети.

Что сделать. Сетевую ошибку без ответа пробрасывать. Анонимный объект оставлять для ответа, в котором сервер явно сообщает об отсутствии пользователя. При ошибке обновления сохранять предыдущие данные кеша.

Приёмка. Пользователь 7 остаётся в кеше после трёх отказов сети. Страницы под RequireAuth не сменяются приглашением войти. Ответ 401 по-прежнему переводит интерфейс в гостевое состояние.

Проверка: repro.test.ts · does not replace the session with an anonymous user. Транспорт заменён отказом без ответа. Ожидаемое поведение нарушено. Штатный набор эту ошибку не выявил.

#2 · P2

Короткий фрагмент имени или почты запрещает пароль

воспроизведено

rsconcept/frontend/src/features/auth/backend/password-validation.ts:51

if (a === b || a.includes(b) || b.includes(a)) {
  return 1;
}

Уверенность: точно. Категория: Безопасность и проверка входных данных.

Сценарий. Регистрация: username ivanov, почта ivanov@example.com, имя Al, пароль PortalPass123. Отдельно проверить пароль против адреса a@b.co.

Ожидаемое и фактическое. Порог в коде равен 0,7. Доля совпадения portalpass123 и al по алгоритму Django SequenceMatcher равна 0,267, с a равна 0,143. Ожидается принятие пароля. Фактически isPasswordTooSimilar возвращает true, и schemaUserSignup отклоняет форму.

Причина. Любое вхождение части поля пользователя в пароль получает коэффициент 1, минуя порог. Части короче осмысленного слова не отсекаются. Из example.com получается часть com, из a@b.co получается часть a.

Ущерб и условия. Клиент не даёт отправить регистрацию с паролем, который порог 0,7 и проверка Django без этого ярлыка пропускают. Достаточно короткого имени или однобуквенной части адреса. Сервер при регистрации вызывает validate_password без объекта пользователя, поэтому сходство с полями на сервере для новой учётной записи не срабатывает. Блокирует именно форма.

Что сделать. Считать коэффициент Левенштейна для каждой части и сравнивать его с 0,7. Не считать короткую часть автоматическим совпадением.

Приёмка. PortalPass123 при имени Al принимается. Пароль, который действительно близок к username или к длинной части почты, по-прежнему отвергается. Существующий тест на ivanov2026 остаётся красным для похожего пароля.

Проверка: repro.test.ts · keeps a password whose only overlap with a user field is a short fragment. Коэффициенты Django посчитаны отдельно через difflib.SequenceMatcher. Штатный тест проверяет только ivanov2026 и не содержит короткой части.

#3 · P2

Нечисловой адрес роняет страницу схемы до её обработки ошибки

воспроизведено

rsconcept/frontend/src/features/rsform/pages/rsform-page/rsform-page.tsx:28

version: z.coerce
  .number()
  .nullish()
  .transform(v => v ?? undefined),

Уверенность: точно. Категория: Безопасность и проверка входных данных.

Сценарий. Открыть /rsforms/12?v=foo&active=bar и отдельно /rsforms/abc. Тот же приём числа стоит у модели, операционной схемы, создания элемента (modelFrom) и шаблонов промптов (active).

Ожидаемое и фактическое. Для неизвестной вкладки уже есть запасное значение. Для нечисловых id, версии и active ожидается страница «не найдено» или игнорирование параметра. Фактически Number('foo') даёт NaN, а z.coerce.number() бросает ZodError: expected number, received NaN. Разбор стоит до ErrorBoundary страницы и до проверки if (!urlData.id).

Причина. z.coerce.number() не отвергает строку заранее и не подставляет запасное значение. nullish пропускает только null и undefined. Вкладка защищена через tabQuerySchema, соседние параметры нет.

Ущерб и условия. Существующая схема с испорченным v или active не открывается. Маршрут показывает общий ErrorFallback и, при включённом Sentry, отправляет исключение. Достаточно набранного или сохранённого адреса. Данные схемы этот запрос не меняет.

Что сделать. Общий разбор целого из адреса: пустое и нецелое значение дают undefined. Для id без числа переходить на страницу «не найдено», для версии и active открывать схему без этих параметров.

Приёмка. ?v=foo и ?active=bar не бросают. /rsforms/abc, /models/abc и /oss/abc показывают «не найдено». Неизвестная вкладка по-прежнему заменяется запасной.

Проверка: repro.test.ts · does not throw on a non-numeric version. Схема страницы не экспортируется, в тесте повторено то же выражение и подключён настоящий tabQuerySchema. Компонент в браузере не монтировался. Переход на ErrorFallback следует из errorElement в router.tsx.

#4 · P2

Новый контекстный поиск показывает совпадения предыдущего

воспроизведено

rsconcept/frontend/src/features/library/backend/use-library-context-search.ts:45

placeholderData: previous => previous

Уверенность: точно. Категория: Прочее.

Сценарий. Контекстный поиск apple вернул ids [1]. Затем ключ меняется на zebra, а новый запрос ещё не завершён.

Ожидаемое и фактическое. Список должен относиться к zebra или быть явно незавершённым. Фактически при fetchStatus: fetching данные остаются [1].

Причина. placeholderData подставляет успешный результат прошлого ключа. matchIds берёт data.ids и не смотрит, что это заполнитель другого запроса. Фильтр библиотеки оставляет элементы с этими id.

Ущерб и условия. Пока сервер ищет новый текст, таблица и выгрузка CSV показывают совпадения старого текста. Поле поиска уже содержит новый запрос, индикатор загрузки стоит на поле, а не объясняет строки. Нужен предыдущий успешный поиск и второй запрос.

Что сделать. Не считать placeholder текущего ответа. До ответа показывать выбранное в разделе решений состояние. Подпись должна отличать его от готового результата.

Приёмка. Во время запроса zebra таблица не содержит набор apple как готовый результат. После ответа остаются только ids нового ответа.

Проверка: repro.test.ts · does not treat a pending or failed search. Наблюдатель TanStack Query с тем же placeholderData. Ожидаемое поведение нарушено.

#5 · P2

Ошибка контекстного поиска показывает всю библиотеку

по коду

rsconcept/frontend/src/features/library/backend/use-apply-library-filter.ts:43

if (contextMatchIds !== null) {

Уверенность: точно. Категория: Проглатывание ошибок.

Сценарий. Контекстный поиск с непустым текстом и выбранными полями завершается сетевой ошибкой.

Ожидаемое и фактическое. Ожидается пустой список или явное сообщение, что поиск не выполнен. Запрос действительно переходит в status: error и data: undefined, это воспроизведено. matchIds при этом становится null. Фильтр при null не ограничивает строки, поэтому таблица остаётся полным текущим набором библиотеки.

Причина. null одновременно значит «запроса нет» и «ответ не получен». Вторая ветка пропускает фильтр. Тост транспорта может появиться, но список выглядит как завершённый показ всех элементов.

Ущерб и условия. После сбоя пользователь видит всю доступную библиотеку при введённом запросе и может выгрузить её как результат поиска. Нужны режим контекстного поиска, непустой запрос и отказ запроса.

Что сделать. Отличать отсутствие запроса от ошибки. При ошибке не показывать неотфильтрованный список как результат. Оставить тост или текст ошибки.

Приёмка. Сбой context-search не оставляет в таблице элементы, которые сервер не вернул. Пустой успешный ответ по-прежнему показывает пустую таблицу.

Проверка запроса: тот же тест, поля failedStatus: error и failedIds: null. Ветка фильтра прочитана в use-apply-library-filter.ts и в браузере не прогонялась. Таблицу как страницу не открывал.

#6 · P2

Короткий поисковый шаблон надолго занимает вкладку

воспроизведено

rsconcept/frontend/src/services/search/text-matcher.ts:24

this.query = new RegExp(query, isCaseSensitive ? '' : 'i');

Уверенность: точно. Категория: Производительность и конкурентность.

Сценарий. Собрать TextMatcher с запросом (a+)+$ и проверить строку из 22 и 24 букв a с хвостом b.

Ожидаемое и фактическое. Короткий запрос в поле поиска должен быстро вернуть да или нет. 22 символа заняли 1153 мс и вернули false. 24 символа не завершились за 4 секунды, процесс убит лимитом.

Причина. Текст пользователя компилируется как регулярное выражение. Вложенный квантификатор заставляет движок перебирать варианты до отказа. Запасной поиск подстроки выполняется только после возврата test, поэтому во время зависания он не помогает. Тот же класс стоит на поиске конституент и на поиске библиотеки по полям карточки.

Ущерб и условия. Один ввод в поле поиска блокирует вкладку. Длина строки около двадцати символов уже достаточна. Это действие самого пользователя или вставленный шаблон, не запрос к серверу.

Что сделать. Ограничить время проверки или не исполнять шаблон с вложенными квантификаторами как выражение. Для такого ввода сразу использовать поиск подстроки, который уже есть для невалидного шаблона.

Приёмка. Запрос (a+)+$ на строке из 24 символов a завершается в отдельном процессе быстрее одной секунды. Обычные шаблоны вроде F\d+ по-прежнему ищутся как выражения.

Проверка: redos-worker.mjs, лимит run-redos-limit.mjs, цифры в results.json. Процесс отдельный. Лимит 4 секунды относится к прогону, не к допустимому времени интерфейса.

Границы проверки

Связки дефектов

  • №4 и №5 портят один список. №4 подменяет его старыми ids, №5 при ошибке снимает фильтр. Исправлять вместе, проверки оставить раздельными.
  • №1 скрывает сетевой сбой успешным анонимным ответом. Пока он есть, легко принять разбор профиля за обычный выход.
  • №3 повторяется в страницах схемы, модели, операционной схемы, создания элемента и шаблонов. Это один приём разбора, не пять дефектов.
  • Штатные тесты не покрывают эти сценарии. Отдельных находок про каждый отсутствующий тест нет.

Ожидания, зафиксированные до чтения реализации

Вошедший пользователь остаётся вошедшим, пока сервер не сообщит об отсутствии сессии. Пустой и неверный адрес не роняют страницу. Пароль сравнивается с полями пользователя по объявленному порогу. Список поиска относится к текущему запросу. Отказ запроса виден как отказ. Короткий ввод в поле поиска завершается быстро. Пустой поисковый запрос по-прежнему показывает все элементы, это уже закреплено тестом.

Отдельного ТЗ на frontend нет. Ожидания взяты из docs/architecture.md, rsconcept/frontend/AGENTS.md, текущих тестов и серверных AUTH_PASSWORD_VALIDATORS. Для непросмотренных экранов выводов нет.

Что не проверено

  • Пакет содержит больше тысячи файлов TypeScript. Построчно просмотрены сессия, пароль, разбор адресов основных редакторов, контекстный поиск, текстовый искатель, выборочно обновление кеша после мутаций, показ HTML-ошибки и запись песочницы. Графы, PDF, онбординг, каталоги переводов и остальные диалоги не объявляются проверенными.
  • Страницы в браузере не открывались. Для №3 и №5 виден результат функции, не снимок экрана.
  • Живой backend, CSRF в браузере и гонка двух вкладок не поднимались. Для №1 заменён только транспорт авторизации.
  • Реестр зависимостей и CVE не проверялись. Импорты в прогнанных сценариях разрешились установленными пакетами.
  • Запись песочницы в IndexedDB не дала подтверждённой потери. Перекрывающиеся saveBundle вызывают put до первого ожидания, отдельный дефект из этого не сделан.
Отчёт следует за ревью domain от 2026-11-01 и за ревью от 2026-10-31, где frontend смотрели выборочно. Код продукта не изменялся.
