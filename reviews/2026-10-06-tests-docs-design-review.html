Tests, documentation & design-completeness review

Date: 2026-10-06 Baseline: b8bf759 Scope: backend, frontend, @rsconcept/domain, rstool, rstool-mcp, CI

This review covers four things: missing tests, missing documentation, design choices that were left half-finished, and checks, restrictions or tests that cost more than they give. It builds on the 2026-10-05 critical design review and does not repeat its findings (CDR-01 to CDR-16).

Verdict

The test suites are broad, but they have holes that nobody can see. Some tests are written and never run. Coverage numbers leave out files that no test imports. Rules that exist in two places have drifted apart, and nothing checks them against each other.

2 high 8 medium 5 low 6 verified by probe

Many findings share one cause. A rule or contract is written by hand in two or three places, such as the RSForm model and its cached twin, the password checks on client and server, the field limits, the contract version, and the rstool method tables. No test checks that the copies still agree. Each copy works alone, but they no longer match.

Missing tests

HighT-01

24 backend tests are written but never run

✓ fixed
apps/library/tests/s_views/__init__.py · apps/users/tests/__init__.py

Backend test files are named t_*.py. Django's default discovery pattern is test*.py, so a test file only runs if its package __init__.py star-imports it. Three modules are missing from those imports, so neither CI nor manage.py test ever runs them:

  • library/tests/s_views/t_context_search.py: context-search ranking and access filtering
  • library/tests/s_views/t_items_by_ids.py: by-ids access control and ordering
  • users/tests/t_docs_views.py: regression guard for OPTIONS returning 500 on the Swagger/ReDoc pages

The full suite reports 378 tests, and none of these appear in the -v 2 listing. Run by name, all 24 pass, so they are good tests that nobody is running.

Fix: remove the need to register files by hand. Either run manage.py test -p "t_*.py" in CI and in package.json scripts and empty the star-import __init__ files (keeping both would run every test twice), or add a meta-test that fails when a t_*.py file is not imported by its package.

Resolved: TEST_RUNNER = shared.discover_runner.PortalTestRunner defaults discovery to t_*.py; star-imports were removed from all test packages. The suite now runs 402 tests (378 + 24) with no duplicates.

MediumT-02

5 of the 13 agent API endpoints have no tests, and 4 of them are writes

✓ verified
apps/agents/views/rsforms.py · apps/agents/views/library.py · apps/agents/tests/t_agents.py

External agents use /api/agents/*. These routes are documented in PORTAL-API.md and have their own throttles and audit log. No test covers rsforms/:id/create-version, constituents/delete, substitute, move-cst or library/by-ids. None of these paths appears anywhere in apps/agents/tests. Each untested write view has its own permission rule (create-version is owner/staff only, the others need edit rights) and its own audit-log summary.

Fix: for each route, test owner OK, editor OK or forbidden, other user 403, read-only item 403, and one audit row written. That is about five cases per route, and they can reuse the existing TestAgentRsformApi fixture.

MediumT-03

No test checks that frontend and backend agree on the API, and frontend CI runs on backend changes anyway

✓ verified
rsconcept/frontend/tests/mocks/* · playwright.config.ts · .github/workflows/frontend.yml

Every Playwright spec runs against hand-written page.route mocks, and no spec talks to Django. The workflow is still triggered by rsconcept/backend/**, so a backend-only change runs the full frontend E2E suite. That suite cannot catch a backend change that breaks the frontend, so a green run is a false signal. AGENTS.md says "API contract changes: sync frontend/backend", but nothing enforces it. The mocks are also mutable shared state, which is why the suite is limited to one worker (see the comment in playwright.config.ts).

Fix: pick one of two options. (a) Commit the generated OpenAPI schema, add a CI check that fails when the regenerated schema differs, and generate or validate the frontend zod DTOs from it. (b) Add one smoke E2E job against a real backend started with SQLite and fixtures. In either case, drop the backend path from the frontend workflow unless (b) is chosen.

MediumT-04

Domain coverage overstates itself, and no package has a coverage gate

✓ verified
rsconcept/domain/vitest.config.ts · all package vitest configs · CI workflows

vitest --coverage reports 78.2% line coverage for @rsconcept/domain. Coverage is only measured for files a test loads, so modules that no test imports are left out of the total entirely:

  • Not loaded by any test: library/oss-layout-api.ts (377 lines, OSS graph geometry) and library/structure-planner.ts (147 lines)
  • 0%: rsform-api/stats.ts, rslang/typification-graph.ts, rslang/semantic/arguments-extractor.ts
  • Low: rsmodel-api.ts 24.5%, rsform-api/cst-type.ts 36.7%, rsengine.ts 44.6%, oss-api.ts 57.6%

Only rstool configures coverage at all, and no CI job enforces a minimum.

Fix: set coverage.include: ['src/**'] so untested files count against the total. Add a thresholds floor at today's level so coverage cannot drop, and test oss-layout-api and rsmodel-api first, since they are pure functions and easy to test.

MediumT-05

Frontend tests are concentrated in the wrong places

✓ verified
src/features/rsmodel · src/features/oss · src/stores · src/features/agents

The onboarding tour has 1,845 lines of tests. Model evaluation (rsmodel, 5.9k lines) and the agents key-management UI have none. OSS has 72 test lines for 7.9k lines of code. These are the pieces most likely to break silently:

  • rsmodel/models/json-file.ts: export payload logic (deduplicating values, falling back to basic bindings)
  • rsmodel/backend/model-sync*.ts: keeping the model in sync between the client and the server
  • stores/preferences-sync.ts: syncing preferences across browser tabs (the cross-tab code in src/backend is tested, but this store is not)

Fix: add unit tests for the three modules above before adding more onboarding tests.

Incomplete design choices

HighD-01

The two RSForm implementations have drifted apart, and the plain one can write a self-attribution

✓ verified
apps/rsform/models/RSForm.py:264 vs RSFormCached.py:264 · Attribution.py

RSForm and RSFormCached both implement substitute, delete_cst, apply_mapping, reset_aliases and insert_last. Both files carry # pylint: disable=duplicate-code. The copies have drifted apart:

  • RSFormCached.substitute skips a remapped attribution when container == attribute. RSForm.substitute does not. A probe test substituted the attribute X1 with its own container N1. The plain version saved the attribution (N1 → N1), and the cached version saved nothing.
  • RSForm.insert_last validates the alias, and RSFormCached.insert_last does not.

The plain version is the one that runs for POST /api/rsforms/:id/substitute, the agent substitute route, inline synthesis (rsforms.py:656) and OperationSchema.py:149. Three other code paths reject self-attribution (data_access.py:62, io_files.py:392, PropagationEngine.py:162), but the database has no constraint against it.

Fix: add CheckConstraint(~Q(container=F('attribute'))) to Attribution with a data migration that deletes existing self-loops. Copy the guard into RSForm.substitute, and add a test that runs each shared method on both classes with the same fixture. In the long run, make one class delegate to the other.

MediumD-02

The rstool method list is written by hand in three places, and invalid filters are silently ignored

✓ verified
rstool/src/models/tool-contract.ts · rstool/src/wrapper/stdio-handler.ts · rstool-mcp/src/tools.ts

Adding a method means editing the RSToolContract interface, the stdio switch plus STDIO_METHODS, and TOOL_DEFINITIONS in the MCP package. Nothing checks that the three lists still match. The code that parses diagnostics filters is also copied, with small differences: stdio still accepts the old nested filters object and MCP does not. Both silently drop an unknown kind or severity. A typo such as severity: "warn" therefore returns all diagnostics with no filter applied, and the caller gets no error.

Fix: export one method table from rstool with the name, how to map arguments, and the JSON schema, and build both adapters from it. Reject invalid enum values with an error. Until then, add a test that checks the stdio method list against the MCP tool names, mapping camelCase to snake_case.

MediumD-03

The Portal JSON contract version has no compatibility rule, and the constant is defined three times

✓ verified
backend/shared/portal_json.py · shared/serializers.py:35 · frontend/src/utils/constants.ts:64 · library/models/portal-import-json.ts · rstool/src/models/portal-json.ts

PORTAL_JSON_CONTRACT_VERSION = '1.0.0' is defined separately in the backend, the frontend and rstool. The @rsconcept/domain package exists to hold shared definitions like this, but does not hold this one. The backend and the frontend both accept only an exact match (!= and z.literal), and the frontend parses with z.strictObject, which rejects unknown fields. As a result, any version bump, even one that only adds a field, makes every file exported earlier unreadable and breaks any client that has not updated. The version looks like semver, but the code does not treat it as semver.

Fix: move the constant into @rsconcept/domain and generate the Python value from it, or check in CI that the copies match. Accept any version with the same major number. Document the format (see DOC-02).

LowD-04

◐ plausible

Unnecessary checks, restrictions & tests

MediumR-01

The client-side password similarity check disagrees with Django's validator

✓ verified
frontend/src/features/auth/backend/password-validation.ts · backend/project/settings.py:367

isPasswordTooSimilar reimplements Django's UserAttributeSimilarityValidator with different logic. Django compares strings with SequenceMatcher.quick_ratio. The client uses Levenshtein distance and also treats any substring match as ratio 1. It splits user fields on /\W+/ without the u flag, so Cyrillic letters count as separators. Results from the same inputs:

PasswordUser fieldsClient rejects?Django rejects?
Truestory2024email ivan.petrov@mail.ruyes (the email part "ru" is a substring)no
Alpha-Centauri7first name Alyesno
иванов2024last name Ивановno (Cyrillic name split away)yes

The client blocks valid passwords, and lets through passwords the server then rejects. The audience is Russian-speaking, and Russian email domains (.ru) and Cyrillic names are common, so both cases come up in normal use.

Fix: remove the client-side similarity check and show Django's field error, which the form can already do. If an immediate client-side warning is wanted, port quick_ratio exactly, use /\W+/u, and add test cases that match Django's results on the same inputs.

MediumR-02

Frontend field limits do not match backend limits

✓ verified
frontend/src/utils/constants.ts:45 · rsform/backend/types.ts:157,187 · auth/backend/types.ts · Constituenta.py:43 · data_access.py:455

One constant, limits.len_alias = 255, is used for fields that have different limits on the server:

  • Constituent alias: the client allows 255 characters, the model allows 8. Anything over 8 reaches the server and comes back as a 400 error instead of an inline message.
  • Username: the client allows 255, Django allows 150.
  • Login and current password: capped at 255 on the client, while the server has no limit. A user with a longer password could never log in from the UI.
  • Batch constituent create: the client only requires .min(1), while the server caps the batch at 100 (CST_BATCH_CREATE_MAX_ITEMS). Cloning more than 100 selected constituents from the RSForm page (use-schema-cst-actions.ts:104) will fail on the server (likely, not run).

Fix: give each field its own limit constant that mirrors the backend (alias 8, username 150), remove the max length on login passwords, and either split clone/template batches into chunks of 100 or cap the selection. A test that compares the frontend limits with the generated OpenAPI maxLength values would stop this drifting again.

LowR-03

Redundant or unreachable checks

✓ verified
rsform/serializers/io_files.py:301,322 · agents/views/rsforms.py:55-66,194-197 · shared/permissions.py
  • Sandbox import item cap checked twice. ListField(max_length=TRS_IMPORT_MAX_ITEMS) already rejects oversized lists before validate() runs, so the second check at line 322 can never trigger.
  • _quota_passed is always true. initial() sets it whenever agent_action is set, and handle_exception then checks both. No quota is checked at this point, so the flag adds nothing, and its name suggests a quota gate that does not exist.
  • create-version validates items, then reads the raw body again. VersionCreateSerializer validates items, but the view then reads request.data['items'] directly. It should use validated_data.
  • hasattr(user, 'is_staff') guards in can_read_library_item, can_edit_item and GlobalAdmin cannot fail, because both User and AnonymousUser define is_staff.
  • The permission "hierarchy" is only inheritance on paper. ItemAnyone extends ItemEditor, which extends ItemOwner, but each class overrides every method, so nothing is actually inherited. Readers will assume a chain of permissions that is not there. Use flat classes that delegate to can_read_library_item and can_edit_item.
LowR-04

Tests that only check Django or the framework

✓ verified
oss/tests/s_models/t_Layout.py · t_Operation.py · rsform/tests/t_serializers.py · 11 files total

There are 19 tests of __str__, field defaults and related_name lookups (for example test_related_name_layout and test_default_data). They check that the Django ORM behaves like the Django ORM. TestExpressionSerializer checks that a required CharField is required. They are cheap to run but add maintenance work and inflate the test count. Replace them with tests of behaviour, starting with the gaps in T-02 and D-01, or simply delete them.

Documentation & tooling gaps

MediumDOC-01

The OpenAPI schema leaves out API-key auth and the key-management endpoints

✓ verified
apps/agents/authentication.py · apps/agents/views/keys.py · manage.py spectacular

Generating the schema produces 14 warnings and 7 errors. No OpenApiAuthenticationExtension is registered for ApiKeyAuthentication, so Swagger lists the 13 agent routes with no security scheme, and the Bearer API key cannot be used from the docs UI. ApiKeyViewSet fails with "unable to guess serializer" and is left out of the schema completely, and its id path parameter comes out with no type. CI never builds the schema, so these warnings appear only when someone runs the command by hand.

Fix: register an auth extension with type: http, scheme: bearer, give ApiKeyViewSet a serializer and an <int:pk> path, and add manage.py spectacular --validate --fail-on-warn to backend CI. That check is also the basis of the contract test in T-03.

MediumDOC-02

The Portal JSON import/export format is not documented

✓ verified
rsconcept/rstool/docs/PORTAL-API.md · README.md

No Markdown file in the repository mentions contract_version. The format is shared by RSForm and RSModel exports, by the agent replace route and by rstool's exportPortal. Its required fields, item shapes, versioning rule (see D-03) and size limits (2 MB on the client, 500 items for TRS/sandbox imports, 100 per batch) can only be learned from three separate parsers.

Fix: add a "Portal JSON v1" section to PORTAL-API.md with a JSON Schema and one example each for RSForm and RSModel.

What is in good shape

  • The backend suite (378 tests) passes in about 33 seconds, and each app has separate model, view and propagation test packages.
  • The agent REST API has user-facing documentation in Russian, covering auth, every route, throttling, retention and 429 handling (PORTAL-API.md).
  • The rstool README and MCP README list every method and are kept in step with contract 3.3.0.
  • The i18n test locale-keys-parity checks that the en, ru and fr key sets match. Many of the drift problems above could be caught by tests of the same kind.
  • The frontend's cross-tab auth and reset logic (src/backend) is thoroughly tested, with roughly as many test lines as source lines.
